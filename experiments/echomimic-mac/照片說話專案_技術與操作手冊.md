## 1. 專案目的與目前成果

將一張人物照片與一段語音交給 EchoMimic，產生包含嘴部變化與人像動作的影片。未來預計把聊天機器人的語音回覆接入，讓使用者看到照片中的人物說出回覆。

目前使用者需提供「照片」與「音訊」兩項輸入。只有照片不能決定要說什麼；本模組也不會從照片推斷人物原聲。

### 已完成

- Apple Silicon Mac 的音訊驅動推論入口移植。
- 九個必要模型檔案下載、大小核對及外接硬碟儲存。
- 照片上傳與預覽、短音訊上傳、麥克風錄音入口。
- 2／10／20 步品質選擇、工作階段與經過時間顯示。
- 單程序工作限制、按鈕防重複提交與取消工作。
- 本次結果預覽、MP4 下載及日誌下載。
- 各工作使用獨立目錄，避免混用上一筆照片、音訊或影片。
- 真實照片搭配 2.1105 秒中文合成語音完成生成。

### 尚未完成或尚未驗證

- 上傳後一秒內生成完整影片。
- 模型常駐記憶體、分段串流播放與即時通話。
- 與主專題的 Gemma 3 4B、身分辨識、PIN、聊天記憶直接串接。
- 精確音素嘴型同步的量化評測。
- Windows／NVIDIA 上使用這份 Mac 測試平台的完整驗證。
- 長影片、正式高解析度、多人照片及所有特殊照片的品質保證。

本版產生的是生成式影片，人物外觀可能變形。成功輸出檔案不代表人物保真或嘴型自然度已達產品標準。

## 2. 實作流程與架構

```text
照片上傳 ─→ 圖片驗證、方向修正、RGB 標準化 ─┐
                                              ├→ 獨立工作設定
語音上傳／錄音 ─→ 長度檢查、單聲道 16 kHz WAV ─┘
        ↓
啟動 EchoMimic 子程序
        ↓
完整讀入照片 → 載入模型 → 人臉定位與裁切
        ↓
Whisper 音訊特徵＋照片參考特徵＋動作模組
        ↓
去噪生成 → VAE 解碼 → 影片編碼
        ↓
FFmpeg 將原始測試語音合成到影片
        ↓
核對影音軌與長度 → 預覽／下載／保存日誌
```

### 為什麼先用獨立測試平台？

先確認照片生成品質、速度與影音同步，再接入聊天機器人，可以分辨問題來自語音生成、照片模型，還是播放流程。

### 為什麼每次都啟動子程序？

首版沿用已完成基本驗證的命令列入口，方便獨立取消、保留錯誤日誌及清理程序。代價是每次重新載入模型，啟動很慢。這是目前設計限制，並非效能最佳方案。

### 為什麼沒有改成快速假嘴型動畫？

使用者希望比較真實模型生成的效果。瀏覽器讓嘴巴開合或讓整張照片晃動，不能等同 EchoMimic 的自然人像生成結果。

## 4. 環境與儲存需求

- MacBook Air M3，16 GB 統一記憶體。
- Mac 內建磁碟存放程式與 Python `.venv`。
- 外接磁碟名稱 `KATHY`，存放模型權重。

## 6. 網頁操作指南

### 6.1 照片

- 建議單人、正面、臉部清楚且光線充足。
- JPEG、PNG 可作為優先測試格式。
- 照片上限 20 MB，最多 2400 萬像素。
- 平台修正照片方向並轉為 RGB，最長邊縮至不超過 1536 像素。
- 模型通常會裁切人臉附近區域；不是保證保留整張全身照片與背景。
- 眼鏡、手部遮擋、帽沿與側臉可能影響輸出，需要實際比較。

### 6.2 聲音

- 接受 0.5～5 秒音訊，檔案上限 30 MB。
- 建議先用 1～3 秒乾淨人聲測試。
- 可以上傳音訊；也可展開麥克風錄製，錄好後按「使用這段錄音」。
- 瀏覽器錄音需要麥克風權限。
- 輸入會轉為單聲道 16 kHz WAV。
- 超過長度範圍會拒絕，不會偷偷截斷。
- 這個平台不提供聲音複製；輸出使用提供的音訊。

### 6.3 品質選擇

| 選項 | 用途 | 注意 |
|---|---|---|
| 快速檢查：2 步 | 確認流程是否跑通 | 先前可見明顯模糊及變形，不能代表正式效果 |
| 效果測試：10 步 | 首輪觀察人物與嘴部效果 | 建議先搭配短音訊 |
| 細節測試：20 步 | 比較較多步數的效果 | 更慢，不保證對每張照片都有改善 |

選擇後按「生成說話影片」。狀態區會顯示目前階段及經過秒數，這不是準確的剩餘時間預測。

### 6.4 預覽、下載與取消

- 完成後在右側播放結果。
- 「下載本次影片」取得含聲音的 MP4。
- 出錯時可下載本次工作日誌，提供組員排查。
- 下方「已完成的官方範例」是舊範例，不是你目前上傳照片的新結果。
- 取消後仍會保留部分工作資料，供檢查；不會自動清空你的資料夾。

## 7. 新電腦重建環境

以下是 **Apple Silicon Mac** 的重建方式，不是已驗證的 Windows 一鍵安裝。

### 7.1 安裝系統工具

先安裝 Git、Python 環境管理工具 uv，以及 FFmpeg。若已安裝 Homebrew，可使用：

```bash
brew install uv ffmpeg git
```

確認命令可用：

```bash
uv --version
ffmpeg -version
ffprobe -version
git --version
```

### 7.2 取得上游與專題補丁

目前功能在 PR #2 的分支；PR 尚未合併時，不能假設下載 `main` 就有本平台。

在準備放置專案的資料夾執行：

```bash
git clone --branch feat/echomimic-mac-validation-20261103 https://github.com/Yun05617/future.git future
git clone https://github.com/antgroup/echomimic.git EchoMimic
cd EchoMimic
git checkout c32b3a557003f84ead1483a2d2386035685d984d
git apply ../future/experiments/echomimic-mac/mac-port.patch
cp -R ../future/experiments/echomimic-mac/overlay/. .
```

補丁是針對指定上游提交製作；不要在未知版本重複套用。若出現 `patch does not apply`，先確認提交與是否已套過補丁。

### 7.3 建立 Python 環境

```bash
uv venv --python 3.10 .venv
uv pip install --python .venv/bin/python -r mac/requirements.txt
uv pip check --python .venv/bin/python
```

不要把其他電腦的 `.venv` 當作可攜環境直接複製。安裝完成後，檢查 MPS：

```bash
PYTORCH_ENABLE_MPS_FALLBACK=1 .venv/bin/python mac/check_device.py
```

此檢查包含 FP16 Conv3d；成功只代表該運算可執行，不代表完整人像生成已成功。

### 7.4 準備權重與啟動

依下一章放置九個權重檔，再執行：

```bash
bash mac/start_test_ui.sh
```

Apple Silicon 的啟動腳本會把 `/opt/homebrew/bin` 加入 PATH。若 FFmpeg 安裝於其他位置，需讓實際安裝位置也出現在 PATH。

## 10. 真實照片實測與速度

### 2026-11-05 成功結果

- 輸入：使用者提供的一張人物照片。
- 語音：「你好，很高興見到你。」
- 聲音：macOS Meijia 合成聲音，非照片人物原聲。
- 音訊長度：2.1105 秒。
- 設定：256×256、12 FPS、10 步，請求 26 影格。
- 最終 MP4：H.264 影片與 AAC 音軌。
- 合成後影片：25 影格、2.083333 秒。
- 音軌：2.111 秒；兩軌皆由時間 0 開始。
- 影音長度差：約 0.0277 秒。
- 完整解碼檢查未報錯。
- 抽查影格可見人物與嘴部變化；仍屬低解析度短片，沒有做音素同步的量化評分。

### 成功一輪的實測時間

| 階段 | 實測時間 |
|---|---:|
| 輸入準備與檢查 | 約 3.82 秒 |
| 啟動 Python／運算套件 | 約 1,033.08 秒（17 分 13 秒） |
| 模型載入與生成前處理 | 約 745.65 秒（12 分 26 秒） |
| 畫面生成、解碼、影音合成與輸出核對 | 約 132.23 秒（2 分 12 秒） |
| **從送出至完成** | **1,914.78 秒（31 分 55 秒）** |

這些階段是由服務每秒觀察日誌估算，不能當成微秒級 profiler 結果。生成與合成合併計時，沒有把 FFmpeg 的數毫秒速度誤當成整段生成速度。

### 前一次失敗

前一次執行在模型載入後，OpenCV 讀圖回傳空值而失敗，耗時 **1,530.25 秒（25 分 30 秒）**。之後獨立重讀時 Pillow／OpenCV 均成功，尚未穩定重現失敗根因；不能直接斷言是照片損壞或中文路徑造成。

已改成載入模型前以 Pillow 完整讀入並保留照片像素，且完成實際照片生成驗證。

兩次生成工作時間合計 **3,445.03 秒（57 分 25 秒）**；不包含兩次之間人工排錯、對話等待與文件整理。成功一輪所需時間應看 31 分 55 秒，不應把失敗時間藏起來，也不應把跨日等待都當成模型運算。

### 如何解讀速度

- 這是單台電腦的單次實測，不是平均值或 90 百分位延遲。
- 大部分時間發生在套件啟動與權重讀取，而非影格生成。
- 本機套件讀取異常慢，需另查儲存與環境狀態；目前沒有足夠證據將其全部歸因於外接硬碟或網路。
- 即使模型已載入，這次約兩秒短片仍花了約兩分鐘完成生成相關階段，尚不符合一秒內出片。

## 11. 影音同步的做法與限制

1. 使用同一份標準化音訊提取模型特徵。
2. 以音訊長度及 12 FPS 計算影格數。
3. 生成影格後，FFmpeg 將該音訊合成進 MP4。
4. 網頁使用單一影片播放器播放，避免畫面與音訊由兩個獨立播放器各自啟動。
5. 核對音軌、畫面軌與長度差；目前容許誤差為 0.15 秒。

必須區分：

- **容器時間一致**：開始時間與長度相近，可由 ffprobe 檢查。
- **嘴型語意一致**：例如發「你」「好」時嘴部動作是否匹配，需要觀看或專門指標評估。

本次完成前者的檢查；不能因此宣稱每個字的嘴型都精確同步。

## 12. 常見問題排查

| 現象 | 檢查方式與處理 |
|---|---|
| 7881 無法連線 | 確認終端機仍執行、是否顯示本機網址；查看平台日誌 |
| 地址已被占用 | 先確認是否已有本平台，不要直接終止不明程序 |
| 首頁卡在 Loading | 檢查前端靜態檔案是否讀取逾時；不能只用開啟公開分享來繞過 |
| `TypeError: unhashable type: dict`／模板錯誤 | 檢查 Gradio 與 FastAPI／Starlette 版本，按 requirements 重建相容依賴 |
| 找不到權重 | 確認 KATHY 掛載、符號連結與九個檔案完整 |
| MPS Conv3d 不支援 | 舊版 torch 2.2.2 曾失敗；本環境已改為 2.8.0 |
| MPS adaptive pooling 非整除尺寸錯誤 | MTCNN 已改為 CPU；不要直接改回 MPS |
| SciPy 動態載入錯誤 | 本機 1.15.3 曾失敗，目前固定 1.14.1 |
| MoviePy 讀片 IndexError | 最後合成已改為系統 FFmpeg |
| 讀圖後出現 NoneType | 使用最新 image_io 補丁，在權重載入前先解碼照片 |
| 成果模糊或變形 | 先確認是否只有 2 步，再比較清楚單人照片與較多步數 |
| 音訊太長 | 自行準備 0.5～5 秒片段，本平台不自動截斷 |
| 明明取消卻又開始 | 使用最新介面，避免多分頁排隊；檢查是否有其他進程或舊版服務 |

### 常用檢查命令

在 EchoMimic 專案根目錄執行：

```bash
uv pip check --python .venv/bin/python
lsof -nP -iTCP:7881 -sTCP:LISTEN
```

查看某一筆工作時，把路徑替換成實際工作編號：


不要只看到 `processing` 就判斷卡死；要同時看程序是否存在、日誌階段是否前進、正在讀取哪個檔案。

## 13. 後續整合聊天機器人

以下是建議設計，尚未實作完成：

```text
使用者說話
→ 身分與情緒辨識／語音轉文字
→ 聊天模型產生回覆文字
→ TTS 產生本次回覆音訊
→ 人像生成服務接收照片識別碼與音訊
→ 完成或緩衝好之後播放同步影音
```

### 第一階段：完整短片模式

- 先用主系統已產生的短音訊，手動上傳到本平台驗證。
- 每一則回覆保留唯一 `reply_id`，對應文字、音訊、照片與影片。
- 同一回覆未完成時不能誤播放上一則影片。
- 明確傳回 `queued / loading / generating / muxing / completed / failed / cancelled` 狀態。
- 若超時，顯示真實狀態並提供繼續等待或只聽語音的選項。

### 第二階段：速度改善

1. 先調查並改善套件啟動耗時。
2. 模型常駐，只在服務啟動時載入一次。
3. 使用者上傳照片後預先完成裁切與可重用特徵。
4. 對每段回覆分別量測 TTS、首影格、完整影片及播放延遲。
5. 再評估分段生成、緩衝與影音共同時間軸。

### 若一秒內開始播放是硬需求

需重新評估生成方法與硬體，不能只縮短網頁動畫或修改進度條。MuseTalk 等即時嘴型方案可列入候選研究，但尚未在本機驗證，也不能拿其他 GPU 的官方速度直接承諾本機表現。

保留獨立模組邊界，避免為了測試照片說話而重寫身分辨識、PIN 或聊天記憶。
